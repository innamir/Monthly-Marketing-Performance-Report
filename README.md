# Monthly Marketing Performance Report
(https://github.com/innamir/Monthly-Marketing-Performance-Report)



## 1. Контекст
Побудований Tableau dashboard для маркетинг-команди, який допомагає аналізувати ефективність рекламних бюджетів за каналами, гео та device OS.

Основна бізнес-задача: зрозуміти, куди варто збільшити бюджет наступного місяця, а де витрати потрібно скоротити.

Дашборд відповідає на питання:

- скільки витратили і скільки заробили;
- який канал має найкращий і найгірший ROAS;
- як змінювалась ефективність по місяцях;
- які geo × channel комбінації працюють краще або гірше;
- чи впливає device_os на payer conversion та ARPU;
- які бюджетні дії рекомендовані на наступний місяць.

## 2. Дані

У роботі використані дві таблиці:

- `spend.csv` — витрати по каналах;
- `users.csv` — користувачі, платники та виручка.

Період даних: `2025-01-01 — 2026-05-13`.

Основні поля:

- `date` / `registration_date`;
- `channel`;
- `geo`;
- `spend`;
- `device_os`;
- `is_payer`;
- `revenue_7d`;
- `revenue_90d`.

## 3. Підготовка даних

Дані були завантажені в BigQuery у dataset:

- `hw-skelar.marketing_report`

Перед побудовою дашборду була проведена перевірка якості даних:

- перевірено діапазон дат;
- перевірено NULL-значення;
- перевірено негативні значення у spend/revenue;
- перевірено дублікати користувачів;
- перевірено значення channel, geo та device_os.

Результат перевірки: дані придатні для подальшої трансформації та аналізу.

## 4. Логіка об'єднання таблиць

Згідно з умовою завдання, таблиця `users` була агрегована до рівня:

`date × channel × geo`

Після цього вона була приєднана до агрегованої таблиці `spend` через поля:

- `date`;
- `channel`;
- `geo`.

Для Tableau були створені дві фінальні таблиці:

- `marketing_dashboard_base` — основна таблиця для KPI, ROAS, каналів та гео;
- `marketing_device_os_base` — окрема таблиця для аналізу device_os.

Device OS винесено в окрему таблицю, тому що у `spend.csv` немає поля `device_os`. Це дозволяє уникнути дублювання spend і некоректного ROAS.

## 5. Методологія ROAS 90D

Основна метрика ефективності бюджету:

`ROAS = revenue_90d / spend`

Оскільки `revenue_90d` накопичується протягом 90 днів після реєстрації користувача, свіжі когорти можуть ще не мати повної 90-денної виручки.

Під час аналізу на monthly trend було помічено різке падіння ROAS у свіжих місяцях. Було зроблено припущення, що це може бути не реальне погіршення каналів, а наслідок недозрілого `revenue_90d`.

Тому для фінальних бюджетних рекомендацій використано лише mature 90D cohorts.

Період для рекомендацій:

`2025-11-01 — 2026-01-31`

Це останні 3 повні місяці, для яких `revenue_90d` вже мав достатньо часу для дозрівання.

## 7. Основні висновки

Email — найефективніший канал за ROAS. Він стабільно знаходиться вище break-even рівня `ROAS = 1`.

Google має ROAS близький до break-even і найвищу payer conversion. Канал не варто різко скорочувати, але масштабувати весь канал без оптимізації також зарано.

Meta показує ROAS суттєво нижче break-even. Канал потребує скорочення бюджету та додаткової оптимізації креативів і аудиторій.

TikTok — найслабший канал за ROAS і payer conversion. Поточний рівень витрат не виправданий результатом.

Device OS аналіз показує, що iOS має найкращі payer conversion та ARPU. Водночас прямий ROAS по OS не розраховується, бо spend не має розрізу `device_os`.

## 10. Рекомендації по Geo та OS

Geo × Channel heatmap показує, що найсильніші комбінації знаходяться всередині Email, особливо у великих гео. Google варто оптимізувати точково, бо частина гео працює ближче до окупності, а частина суттєво нижче break-even.

Device OS використовується як додатковий сигнал для таргетингу. iOS має найкращі payer conversion та ARPU, тому можна тестово зміщувати трафік у бік iOS там, де це доступно в рекламних налаштуваннях.

Водночас не варто приймати великі бюджетні рішення тільки на основі OS, бо spend не має розрізу `device_os`, а отже прямий ROAS по OS не розраховується.

## 11. Припущення та обмеження

- Для бюджетних рекомендацій використовується `revenue_90d`, бо вона краще відображає довшу цінність користувача.
- Для уникнення заниження ROAS свіжі недозрілі 90D-когорти не використовуються у фінальних рекомендаціях.
- `revenue_7d` може бути корисною як ранній індикатор, але не є основною метрикою для бюджетних рішень.
- ROAS по device_os не розраховується, бо у `spend.csv` немає поля `device_os`.
- Рекомендації по зміні бюджету є практичними тестовими діями, а не гарантією збереження ефективності після масштабування.
